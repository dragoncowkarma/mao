# Shipping and Git conventions

Tier 3 reference — read when you branch, commit, push, open or merge a PR, claim a SHA passes, tag a release, or make any external write. Rule summary: [AGENTS.md](../../../../AGENTS.md). Playbook: [SKILL.md](../SKILL.md).

## Before any external write

- Each external write needs explicit task authorization for that specific write. A request to analyze,
  review or verify authorizes none.
- Covered, on this repo or any target repo: create or close issues; push branches; open, comment on,
  approve or merge PRs; create releases; delete refs.
- Also covered, since they drive the pipeline that performs those writes unattended: enqueueing a
  workflow task, `mao run`, `npm run dev` (boots the real host), `mao swarm` (except
  `--dry-run`/`--status`), `refreshRepo`, and the E2E harness `scripts/test-workflow.ts`.
- Also a release: closing, merging or demilestoning the last open item of a milestone titled `vX.Y.Z`,
  or closing that milestone (next section).

## Secrets

- Never commit `.env` / `.env.*`: real tokens and API keys live in `.env.test` (gitignored, absent from
  a fresh clone).
- Never print `githubToken` or a provider `apiKey`; follow `mao config show`'s `'[set]'` redaction.
- Never log or commit store files (`config.json`): the backends hold the GitHub token in plain text.
- `mao config set-token <token>` puts the token in argv, so it can land in shell history and process
  listings. Prefer the Electron settings UI for real tokens. Never run it with a real token from an agent
  terminal, or paste one into an example.
- Token in workspace clones: [workflow-and-routing.md](workflow-and-routing.md).

## When naming a branch

These conventions bind every contributor and AI agent. Manual: `<type>/<issue-number>-<kebab-case-description>`

- `type` (required): `feat`, `fix`, `chore`, `docs`, `refactor`, `test`.
- `issue-number` (recommended): GitHub issue number; may be omitted for small work with no issue.
- `description` (required): concise kebab-case English.
- Examples: `feat/42-add-dark-mode`, `fix/15-broken-ci-gate`, `docs/update-readme`,
  `chore/bump-dependencies`.

Generated by code or tools, so exempt:

| Source | Pattern | Example |
| --- | --- | --- |
| Workflow engine | `workflow/<issue>-<slug>` (no issue: task id's first 8 chars) | `workflow/7-provider-override` |
| Swarm Worker | `worker/<issue>-<worker-slug>-<description>` | `worker/42-claude-add-dark-mode` |
| AI agent (Claude) | `claude/<kebab-topic>-<hex>` | `claude/ai-agent-setup-c92049` |
| AI agent (Codex) | `codex/<kebab-topic>` | `codex/ai-agent-setup` |

## When writing a commit message

[Conventional Commits](https://www.conventionalcommits.org/), in English.

```
<type>(<scope>): <subject>

<body>

<footer>
```

| Field | Required | Rule |
| --- | --- | --- |
| type | yes | Table below |
| scope | no | Table below |
| subject | yes | Imperative mood, sentence case, no trailing period, at most 50 chars |
| body | non-trivial changes | Wrap at 72 chars; explain root cause and rationale |
| footer | no | `BREAKING CHANGE:`, `Closes #<n>`, `Refs #<n>` |

| Type | Use |
| --- | --- |
| `feat` | New feature |
| `fix` | Bug fix |
| `chore` | Build, dependencies, config; non-functional |
| `docs` | Documentation |
| `refactor` | Structure only, no behaviour change |
| `test` | Add or change tests |
| `style` | Formatting, semicolons; no effect on meaning |
| `perf` | Performance |
| `ci` | CI configuration |

| Scope | Covers |
| --- | --- |
| `core` | `core/` |
| `cli` | `cli/` |
| `electron` | `electron/` |
| `ui` | `src/` (React renderer) |
| `ai` | `core/ai/` |
| `workflow` | `core/workflow-engine.ts` and related |
| `github` | `core/github-service.ts` and related |

Nothing enforces these tables; history also has `swarm`, `store`, `agents`. Choose from the table.

Simple:

```
fix(ui): Correct dark mode toggle state on reload
```

Non-trivial:

```
feat(ui): Add dark mode toggle to settings panel

The system-preference detection uses matchMedia('prefers-color-scheme')
and falls back to the stored user preference on load.

Closes #42
```

Breaking:

```
refactor(core)!: Change MaoStore interface to async

All store methods now return Promise. This requires updates to both
electron/store.ts and FileStore implementations.

BREAKING CHANGE: MaoStore.get() and MaoStore.set() are now async.
Closes #50
```

## When titling or merging a PR

- Title: the commit format, `<type>(<scope>): <subject>`.
- Body: link the issue with `Closes #<number>` or `Fixes #<number>`.
- Base: `main`. The convention is a merge commit, but GitHub allows all three methods and 9 of `main`'s
  last 10 merges are squashes (2026-11-03). A squash of several commits takes the PR title as its subject;
  a single-commit PR keeps that commit's subject (`squash_merge_commit_title`: `COMMIT_OR_PR_TITLE`).

## When tagging

[Semantic Versioning](https://semver.org/): `v<major>.<minor>.<patch>`, such as `v0.1.0`, `v1.0.0`,
`v1.2.3`. Pre-release: `v1.0.0-alpha.1`, `v1.0.0-beta.2`. Authorization: step 13 below.

`.github/workflows/release.yml` tags and publishes automatically: when a milestone titled `vX.Y.Z` has no
open and at least one closed item, any close or demilestone event on one of its issues or PRs (or closing
the milestone) builds, then runs `gh release create` at `main`'s head, unless that release exists. So
merging a milestone's last PR is a release action: it needs the same explicit authorization.

## When claiming a SHA passes

- Verification runs the current filesystem, not a Git object.
- A blank `git status --short` proves only that no non-ignored source changed. Ignored artifacts
  (`dist/`, `dist-electron/`, `dist-cli/`, `node_modules/`), `.env*` files and ambient environment
  variables still influence the commands.
- In a dirty or mixed worktree, unstaged edits can make validation pass for code the commit omits.
- Strong exact-SHA evidence needs an isolated detached worktree, a fresh install and a controlled
  environment:

```bash
git worktree add --detach "<dir>" "<sha>"
cd "<dir>" && npm ci
npm run lint && npm run test && npm run test:origin && npx vite build
```

CI (`.github/workflows/ci.yml`) runs on pushes to `main` and all PRs, Node 22, in order:
`npm ci`, `npm run lint`, `npm run test`, `npm run test:origin`, `npx vite build`,
`npm run build:cli`, `npm run test:swarm-bundle`. Locally, with
dependencies installed, run the last line of the block above.

`main` has no branch protection or rulesets (2026-11-03). Re-check:
`gh api repos/dragoncowkarma/mao/branches/main --jq .protected`,
`gh api repos/dragoncowkarma/mao/rulesets`. Green CI is convention, not a GitHub-enforced gate: treat
it as required. The app's own merge-stage gate (`getChecksStatus`) is separate:
[workflow-and-routing.md](workflow-and-routing.md).

CI builds and smoke-tests the CLI bundle. After touching `cli/` or `core/`, run
`npm run build:cli`, `node dist-cli/index.cjs --help` and `npm run test:swarm-bundle` locally too. Other per-area runs: the verification matrix
in [SKILL.md](../SKILL.md).

## When shipping a change

1. **Record the starting state** before any branch: `git status --short --branch`. Note the branch or
   detached HEAD and pre-existing changes: they may be another tool's, and `git checkout -b` would carry
   them onto your branch.
2. **Confirm `origin` itself** before any fetch, branch or push (this repository:
   `github.com/dragoncowkarma/mao`):

   ```bash
   node scripts/check-origin.mjs "github.com/<owner>/<repo>"
   ```

   - Exit 0 prints `OK: every origin fetch/push URL is <expected>`. Exit 1 prints `FAIL(url <n>): <category>`
     or `FAIL: <reason>` lines, then `ORIGIN CHECK FAILED` unless origin could not be listed: stop on the
     exit code, not the text. Exit 2 is a bad invocation.
   - Matches every effective fetch and push URL on scheme, real authority and exact path; fails closed;
     prints fixed categories, never a remote-derived string. Proof: `scripts/check-origin.test.mjs`
     (`npm run test:origin`), except the scheme clause: no case uses `http://` or `git://`, so
     `scripts/check-origin.mjs`' protocol check is unpinned.
   - The argument form works in every shell (PowerShell and cmd have no inline env syntax);
     `MAO_EXPECTED_REMOTE` is the fallback.
   - Never use `gh repo view` as evidence: `gh repo set-default` can point it away from `origin`.
   - Never use a field-split one-liner: it blesses `https://evil.example/github.com/<owner>/<repo>.git`,
     can echo credentials from malformed URLs, and misses a divergent `remote.origin.pushurl` (git pushes
     to every configured push URL).
3. **Pin every later `gh` command** with `--repo <owner>/<repo>`.
4. **Branch from the current `origin/main`**, never local `main`, which can lag by many commits. Record
   the base SHA for step 11. Reuse your own same-scope PR instead of opening a duplicate. Never reuse or force-push a sibling
   tool's branch: open a distinctly named one and say so in the PR.

   ```bash
   git fetch origin
   git rev-parse origin/main
   gh pr list --repo <owner>/<repo> --state all
   git worktree add -b <branch> "<dir>" origin/main
   ```

5. **Stage only the task's paths**: `git add -- <path>...`. Avoid `git add -A` in a worktree that may hold
   unrelated changes. Never stage `.env*`, `dist/`, `dist-electron/`, `dist-cli/`, `release/`, store/config
   files, anything containing a token, or a symlinked `node_modules` (`.gitignore`'s `node_modules/`
   matches a directory only).
6. **Check staged paths**: `git diff --cached --name-status`. Every path must be intended; unstage the
   rest. Run steps 6-8 in this order, printing no potential secret before step 8. Plain `git diff`
   compares worktree to index and misses staged content.
7. **Scan for staged secrets**: `gitleaks git --pre-commit --staged --redact --verbose`.
   - Use a vetted, version-pinned scanner that reports only rule/path/line and redacts values.
   - Run from the repository root: gitleaks diffs pathspec `.`, so a subdirectory scans only itself.
   - Exit 0 with no `ERR` line is clean; outside a repo 8.30.1 logs `ERR` and `no leaks found`, then exits 0.
     1 is leaks found (`--exit-code` default) or a scanner fatal; 127 is not installed; neither is clean.
     Read the exit code from the command itself, not through a pipe.
   - Confirm the installed version supports the flags before trusting its exit code. Never use
     `gitleaks protect`: deprecated and hidden since v8.19.
   - Never gate on a keyword grep: it misses real formats (`sk-proj-…`, `AKIA…`), flags code that merely
     says `token`, inverts its exit code on a clean result, and is absent from Windows' default shell.
   - No vetted scanner: never print the content diff to hunt for secrets. A human reviews the staged
     content (not just the path list) in a local viewer that does not persist to shared terminal or agent
     logs, and explicitly attests it holds no secrets; that substitutes for a clean scan. With neither,
     stop; the workflow does not resume.
8. **Only once step 6's paths are approved and step 7 is clean (or a human attested), read content**:
   `git diff --cached --check`, then `git diff --cached -- <path>...`. On exit 1, never print the diff,
   which may hold the secret: act on the redacted rule/path/line, then re-scan. Never treat a scan result,
   least of all a keyword-grep zero, as permission to dump unrestricted diffs.
9. **Commit** in the format above (imperative subject, why-focused body), then run the full verification
   at the committed head; for strong evidence use the isolated worktree above.
10. **Re-run the guard, then push**, on the final branch:

    ```bash
    node scripts/check-origin.mjs "github.com/<owner>/<repo>"
    git push --set-upstream origin <branch>
    ```

    - The guard must exit 0 again: branch-scoped config (`includeIf "onbranch:…"`) can swap
      `origin.pushurl` the moment the branch exists, so step 2 is stale by push time. Proof: the `onbranch`
      case in `scripts/check-origin.test.mjs`.
    - Never a bare `git push`: `remote.pushDefault` and `branch.<name>.pushRemote` can point it at a
      remote the guard never validated.
    - Pushing and opening a PR are external writes: only when the task calls for them.
    - Never `--force*` unless the user explicitly approves history replacement; authorization to push or
      open a PR does not include it.
11. **Open a draft PR, then verify what was published.** Stay draft unless the user asked for
    ready-for-review or an existing PR already carries an intentional review state.

    ```bash
    gh pr create --repo <owner>/<repo> --base main --head <branch> --draft --title "<t>" --body-file <f>
    gh pr view <number> --repo <owner>/<repo> --json url,state,baseRefName,baseRefOid,headRefName,headRefOid,isDraft,mergeable,mergeStateStatus,reviewDecision,statusCheckRollup
    git merge-base --is-ancestor <recorded-base-sha> <head-sha>
    ```

    - Pin repo and PR number: current-branch inference exits 1 on a detached checkout.
    - Must match the intended base branch, head branch, exact head SHA (`headRefOid`) and draft state.
      Green CI alone proves none of these.
    - Record `baseRefOid` as a snapshot, not the current tip: it is set when the PR opens, a later head push
      refreshes it only sometimes, and `main` moving does not (2026-11-04: #98 holds 32741b4 with `main` at
      bf72203). Never require it to equal the recorded SHA or read it as "`main` has not moved".
      For step 12 compare `gh api repos/<owner>/<repo>/commits/main --jq .sha`. Lineage is the check:
      `merge-base` must exit 0.
12. **Before merging, get green CI for the current base** (lint, test, test:origin, vite build).
    - If the base advanced past the recorded SHA, never credit the existing green rollup. The bare
      `pull_request` trigger runs on opened/synchronize/reopened, so a base-only move starts no run, and
      the old run's `GITHUB_SHA` was the merge against the then-current base. Cross-check which SHA a run
      validated before crediting it.
    - Current-base evidence is one of: with explicit authorization (it rewrites the published head),
      updating the head branch against the current base so a `synchronize` run validates the true merge;
      or building base+head in an isolated worktree, running the matrix, and reporting it as local,
      distinct from GitHub CI.
    - With neither, report current-base CI as unverified and stop before merging.
    - Report commit, push, PR creation, CI, review and merge as separate states; never equate them.
13. **Releases are a separate authorization.** Never tag, publish, sign, notarize or announce without an
    explicit request and evidence for the target platform. `npm run build` and `npm run dist` are local
    packaging, not deployment proof.

## Definition of Done: documented gaps

A PR that closes a documented gap or moves a rule moves or deletes that doc entry in the same commit, since
a stale entry presents a fixed bug as current behaviour. Checkbox: `.github/pull_request_template.md`.

## Agent roles

Mirror the product's maker-checker principle:

- **Planner/Architect:** reads `AGENTS.md` and [SKILL.md](../SKILL.md), scopes the change, lists the
  lockstep files affected.
- **Implementer:** changes `core/` first, then wires the shells (Electron IPC chain and/or CLI command) so
  GUI/CLI parity holds, then the UI.
- **Reviewer:** a different agent or session from the implementer unless none is available. Verifies the
  invariants, runs the verification above, checks no secrets or build outputs are staged. Checklist:
  [repo-preflight-and-swarm.md](repo-preflight-and-swarm.md).
