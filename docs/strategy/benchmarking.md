**MAO가 뒤처진 점(거의 모든 경쟁 제품이 갖춘 것).** diff를 읽는 리뷰(B2), 리뷰 결과에 따른 수정 루프(N1), 트리거 게이팅(A1), 자기 PR 승인 금지와 머지 전 사람 승인(B3, N6), 격리와 자격증명 보호(A2, N9), 실시간 상태와 알림(N3, N7).

**남는 차별점.** 벤더를 가로지르는 검증을 파이프라인 규칙으로 강제하는 것, 그리고 코드를 외부에 올리지 않고 자신의 구독과 키로 돌리는 것입니다. 조사 범위에서는 교차 벤더 검증을 규칙으로 강제하는 제품을 찾지 못했습니다. 가장 가까운 것은 Claude Code 안에서 Codex로 교차 리뷰하는 커뮤니티 skill과, 여러 에이전트에 같은 작업을 맡겨 비교하라는 Agent HQ의 안내입니다. 찾지 못했다는 것이지 없다는 증명은 아닙니다.

## 3. 플랫폼의 이슈→PR 에이전트와 가드레일

| 플랫폼 | 트리거와 가드레일 | 확인 수준 |
| --- | --- | --- |
| GitHub Copilot 클라우드 에이전트, Agent HQ | 이슈를 Copilot·Claude·Codex에 할당(공개 프리뷰, 상위 요금제). 쓰기 권한자만 트리거, 요청자는 그 PR을 승인할 수 없음, 에이전트는 PR을 ready로 바꾸거나 머지할 수 없음, Actions 실행은 사람 승인 | 확인 |
| Claude Code | GitHub Actions(`@claude`), 클라우드 세션, PR 자동 수정, 다중 에이전트 Code Review. 쓰기 권한자만 트리거, 봇 허용 목록 | 확인 |
| OpenAI Codex | `@codex review`와 자동 리뷰, 높은 심각도만 지적, 저장소의 AGENTS.md 리뷰 규칙을 따름 | 부분 확인 |
| Cursor | Bugbot과 Autofix, 클라우드 에이전트 | 부분 확인 |
| Devin, Jules, Kiro, OpenHands | 리뷰 코멘트 자동 수정, 라벨·멘션으로 옵트인 트리거 | 부분 확인 |

벤치마킹할 것:

1. **트리거는 옵트인이고 권한자만 겁니다.** 모든 새 이슈를 자동으로 집어 가는 구조는 업계 관행과 반대입니다. (A1)
2. **에이전트는 머지하지 않거나, 사람의 승인을 거칩니다.** (B3)
3. **리뷰 코멘트가 수정으로 이어지는 닫힌 루프.** (N1)
4. **플랫폼의 에이전트를 감독하는 길.** 실행을 직접 하지 않고, GitHub에서 할당된 에이전트의 PR을 관찰하고 교차 검증하는 계층이 될 수 있습니다. 아직 프리뷰 기능이므로 읽기 전용 관찰부터입니다. (L2)

## 4. 리뷰가 신뢰받는 조건

리서치가 정리한 공통 조건입니다.

1. 리뷰어는 작성 세션과 맥락을 공유하지 않는 새 세션입니다.
2. 입력은 실제 diff, 이슈 본문, 주변 코드, 저장소 규약입니다. 가능하면 테스트와 CI 로그 같은 실행 증거를 더합니다.
3. 후보 지적을 만든 뒤 별도 단계에서 검증해 오탐을 거르고 심각도를 매깁니다.
4. 결과는 구조화된 판정이고, 머지 단계가 그것을 읽습니다.
5. 새 커밋이 올라오면 이전 판정은 무효가 되고 다시 리뷰합니다.
6. 효과는 자신의 정답 세트로 측정합니다. 공개된 벤치마크 수치는 벤더마다 서로 모순됩니다.

**maker-checker 주장의 근거와 한계.** 같은 맥락에서 자기 행동을 평가하면 위험을 덜 지적한다는 연구(arXiv 2603.04582, 초록 확인)가 있고, 사전 맥락이 없는 리뷰어가 가장 잘 작동했다는 실무 보고가 있습니다. 반면 저자를 가리면 자기 선호가 사라진다는 연구도 검색 요약으로 확인됩니다(원문 미확인). 따라서 "다른 벤더라서 더 정확하다"는 직접 증거는 약합니다. 주장은 "작성 맥락과 분리된 독립 검증 단계를 거치며, 가능하면 다른 계열의 모델이 맡는다"로 쓰고, 실제 보장은 CI와 저장소 규칙 같은 결정적 게이트에 둡니다. 더 강한 주장을 하려면 자체 비교 실험이 필요합니다. (B5, N8)

**방어할 수 있는 자동 머지 정책.** 기본은 사람 승인, 낮은 위험만 옵트인 자동 머지입니다. 필수 CI(검사가 없으면 사람 승인), 차단 지적이 없는 판정, 새 커밋 시 승인 무효화, 경로 기반 등급(문서와 테스트는 자동 가능, 의존성·CI 설정·인증·비밀은 항상 사람), 변경 크기 상한, head SHA 고정, AI 작성 표기. (B3, L5)

## 5. 오케스트레이션 패턴

**채택 순위.**

1. 맥락이 분리된 독립 리뷰어 (B2)
2. 탐색 뒤 검증하는 2단계 리뷰와 심각도 (B2)
3. 리뷰 지적을 작성자에게 되돌리는, 횟수 제한이 있는 수정 루프 (N1)
4. 실행에 의한 검증 (N2)
5. 위험 등급별 머지 정책과 사람 게이트 (B3)
6. 단계 사이의 구조화된 인수 산출물: 계획과 수용 기준, 판정 (B1, N1)
7. 외부 쓰기의 멱등성과 체크포인트 (C2)
8. 이슈와 PR을 상태 저장소로 쓰는 기억 (이미 보유)
9. worktree 기반 격리 (C1)
10. 실행당 비용과 토큰 상한 (N3)

**피할 것.** 여러 에이전트가 동시에 쓰는 스웜, 역할극식 "소프트웨어 회사" 시뮬레이션, 무거운 스펙 문서 체계, 범용 에이전트 프레임워크 이식, 서버형 내구 실행 엔진의 조기 도입, 벤더 벤치마크 수치 인용.

**구조에 대한 판단.** 범용 그래프 엔진이 아니라, 지금의 직선 파이프라인에 계획(선택)·수정 루프·검증 단계를 더한 작은 상태 기계가 맞습니다. 지금 필요한 것은 실행 엔진이 아니라 단계별 멱등성입니다.

## 6. 코딩 에이전트 통합

- 주요 CLI는 구조화된 헤드리스 모드(JSON이나 이벤트 스트림), 세션 재개, 권한·샌드박스 설정을 제공합니다. MAO는 프롬프트를 stdin으로 넣고 stdout 전체를 문자열로 받으므로 진행 상황, 비용, 한도 신호를 얻지 못합니다. (N3)
- 2026-11-12에 1차 문서에서 확인한 것: Claude Code CLI는 `--model`, `--effort`, `--output-format`, `--json-schema`를 문서화합니다. Codex의 `exec`는 `--model`, `-c`(설정 값), `--json`, `--output-schema`를 문서화하고 `--effort`는 없습니다. MAO는 모든 CLI에 `--effort`를 붙입니다. (B6)
- 권한 확인을 끄는 옵션과 샌드박스는 별개입니다. 확인을 꺼도 샌드박스를 켤 수 있지만, MAO는 샌드박스를 켜지 않습니다. (N9)
- 권고 구조는 세 층입니다. MAO가 소유하는 정책 층(샌드박스 요구, 토큰 발급, 승인, 출력 검사), 에이전트별 구조화 어댑터와 능력 표, 그리고 나중에 추가할 보편 경로인 Agent Client Protocol 클라이언트(L3).
- MAO를 MCP 서버로 노출하는 것은 지금은 권하지 않습니다. 새로운 신뢰 경계가 생기고 사양이 계속 바뀌고 있습니다.
- Aider, Goose, Amp, OpenCode의 세부 플래그는 확인하지 못했습니다.
