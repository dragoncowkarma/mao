## 1. 판정

**방향은 맞고, 큰 방향 수정이 필요합니다.** 다섯 개 감사 렌즈가 모두 같은 판정(needs-major-course-correction)을 냈습니다.

- 맞는 것: "한 AI가 만든 변경을 다른 AI가 검증해야 머지된다"는 목표입니다. 플랫폼 벤더는 자사 모델로 작성과 리뷰를 모두 하려 하므로, 벤더를 가로지르는 검증을 규칙으로 강제하는 계층은 독립 도구가 설 수 있는 자리입니다([benchmarking.md](benchmarking.md)).
- 어긋난 것: 지금 코드에서는 그 검증이 일어나지 않습니다. 그리고 지난 두 달의 작업은 이 격차가 아니라 `config.json` 손상 방어와 UI 외관에 쓰였습니다.

## 4. 분야별 발견

각 항목 끝의 괄호는 [roadmap.md](roadmap.md)의 항목 id입니다.

### 4.1 제품과 에이전트 시스템

- 리뷰와 머지가 검증 역할을 하지 못합니다(2절 1, 2). 비도구 경로의 시스템 프롬프트는 저장소에 대한 언급 자체를 금지합니다(`core/ai/cli-provider.ts:4-8`). (B1, B2, B3)
- 메모 파일만 담긴 PR이 머지될 수 있습니다(2절 4). (B4)
- maker-checker가 "직전 단계, provider id" 기준이라 작성자가 머지 단계를 맡습니다(2절 5). (B5)
- 엔진이 둘입니다. WorkflowEngine은 직선 4단계에 판정도 수정 루프도 없습니다. Swarm은 수정 루프, 신뢰 코멘트 필터, 벤더 계열 구분이 있지만 승인을 산문 패턴으로 판정하고 머지를 에이전트에게 맡깁니다. 같은 기능을 양쪽에 따로 넣는 비용이 커지고 있습니다. (N1)
- 실행 증거가 없습니다. 테스트를 돌리는 단계가 없고 CI가 없는 저장소는 `none`으로 통과합니다. (B3, N2)
- 한도 초과나 빈 출력의 처리가 구분되지 않습니다. 감사는 한도 안내문이 그대로 GitHub에 게시될 수 있다고 추정했습니다(확인 수준: likely). (B7)
- 실행 중 출력, 사용량, 비용, 조합별 성공률을 볼 수단이 없습니다. (N3, N8)

### 4.2 보안과 GitHub 플랫폼

- 가장 심각한 시나리오: 공개 저장소에 이슈를 하나 엽니다. 그 제목이 권한 확인이 꺼진 에이전트의 프롬프트가 되고, 에이전트는 `.git/config`와 `../../config.json`에서 토큰과 API 키를 읽을 수 있으며, 에이전트의 출력은 걸러지지 않고 PR 본문으로 게시됩니다(2절 3, 6, 7, 9). 네트워크 차단으로는 막을 수 없는 경로입니다. (A1, A2, A3)
- 같은 토큰으로 에이전트가 기본 브랜치나 `.github/workflows`에 직접 push할 수 있습니다. README는 classic `repo` 스코프에 `workflow` 스코프까지 권합니다. (A2, A5, B3)
- 이슈 본문의 지시 태그(`[Model: …]`, `[Worker: …]` 등)를 작성자 확인 없이 적용하므로 외부인이 비용과 검증자를 고를 수 있습니다. (A1)
- 머지 호출이 확인한 head SHA를 고정하지 않습니다. 검사와 머지 사이에 올라온 커밋도 함께 머지됩니다. (B3)
- 모든 단계가 한 GitHub 계정으로 동작합니다. GitHub는 작성자의 자기 승인을 막으므로 필수 승인 규칙과 양립할 수 없고, maker-checker가 GitHub 쪽에는 보이지 않습니다. (N6)
- 렌더러: CSP와 탐색 차단이 없고 비밀이 렌더러로 전달됩니다(2절 12). 마크다운 렌더링(#100)보다 먼저 닫아야 합니다. (A4)
- 릴리스 워크플로: 워크플로 전체에 쓰기 권한, 태그로 고정한 액션, 서명과 체크섬 없는 산출물. `pull_request_target`을 쓰지만 PR 코드를 체크아웃하지 않아 전형적인 취약 패턴은 피했습니다. (D4)
- 잘 된 것: 셸 없는 프로세스 실행, git 오류의 토큰 가림, Electron 기본 보안 설정 유지, self-update가 아무것도 내려받지 않는 점, 권한을 확정할 수 없을 때 "미확인"으로 보고하는 사전 점검.

### 4.3 아키텍처와 신뢰성

- 크래시 일관성이 없습니다(2절 10). 외부 쓰기 직후가 아니라 단계가 끝날 때만 상태를 저장하므로, 중간에 죽으면 같은 쓰기를 반복합니다. (C2)
- 공유 클론과 프로세스 정리 문제(2절 7, 8)는 결과의 정확성을 직접 해칩니다. (C1)
- 전역 직렬 큐라 한 저장소의 15분짜리 단계가 모든 저장소를 세웁니다. CI가 진행 중이면 오류로 끝나 사람이 다시 눌러야 합니다. (N5)
- 비밀, 설정, 큐, 실행 이력이 JSON 파일 하나에 있고 스키마 버전이 없습니다. 방어 코드가 커진 근본 원인입니다. (N4)
- Electron 33은 2025-04에 지원이 끝났습니다. 2026-11-12 공식 일정 기준으로 지원 중인 메이저는 43, 44, 45입니다. (A4)
- Windows 산출물을 내지만 Windows에서 실행 경로를 검증한 적이 없습니다. (D2, 유지보수자 결정)
- 잘 된 것: Electron에 의존하지 않는 core와 단일 부팅 경로, 일부 GitHub 쓰기의 멱등 처리(#37, #38), 요청별 시간 제한, 원자적 파일 교체.

### 4.4 UX, DX, 문서

- 저장소를 추가하면 무인 머지 파이프라인이 바로 켜집니다. 첫 화면은 한 문장뿐이고 연결 테스트가 없습니다. (A1, E2)
- 실행 중이거나 대기 중인 작업을 멈추거나 지울 방법이 GUI에도 CLI에도 없습니다. (C3)
- 실행 중에는 프롬프트와 표시등만 보입니다. diff, 검사 상태, 리뷰 판정, 머지 승인 화면이 없습니다. (N7)
- 여러 저장소를 가로질러 "지금 내가 결정할 것"을 보여 주는 화면과 알림이 없습니다. (N7)
- CLI의 `workflow enqueue`·`retry`·`advance`는 대기 중인 작업 전체를 출력 없이 실행합니다(확인 수준: likely). 토큰을 명령 인자로 받습니다. (C4, E1)
- 사람이 읽는 문서가 README 하나입니다. 운영 지식은 에이전트용 문서 안에만 있습니다. (E3, A5)
- UI 백로그(#96, #97, #100, #102, #108)는 대부분 위 흐름을 개선하지 않습니다.

### 4.5 QA, 릴리스, 개발 프로세스

- 테스트 1.8만 줄이 "리뷰가 머지를 막는다"를 증명하지 않습니다. 실제 CLI와 GitHub를 지나는 경로는 CI 밖에 있습니다. (D1)
- 릴리스가 멈춰 있습니다(3절). 해결된 이슈와 사용자에게 보이지 않는 항목이 릴리스 마일스톤을 막고 있습니다. (N10, 백로그 정리)
- 패키징된 앱의 업데이트 배너가 `main` HEAD를 기준으로 삼아, 릴리스 뒤 머지가 하나만 있어도 "새 버전"을 띄우고 재시작해도 달라지지 않습니다. `mao --version`은 `0.1.0`으로 고정돼 있습니다. (D3, D2)
- CI가 실제로 출시하는 산출물(CLI 번들, 패키지)을 만들지 않습니다. (D2)
- 프로세스: PR 추가 줄 수의 중앙값이 8월 231, 9월 940, 10월 1,659로 커졌습니다. 같은 이슈를 여러 도구로 구현해 하나를 고르는 방식 때문에 #72는 세 번(#74, #95, #93), #60과 #67도 여러 번 구현됐습니다. 리뷰 라운드마다 범위가 넓어지는 것을 되돌리는 장치가 없습니다.
- 잘 된 것: PR마다 도는 CI, 재실행해도 안전한 릴리스 워크플로, 뮤테이션으로 테스트를 검증하는 습관, 과장된 주장을 스스로 철회하는 PR 기록.

## 5. 바깥 환경

자세한 내용과 출처, 확인 수준은 [benchmarking.md](benchmarking.md)와 [user-needs.md](user-needs.md)에 있습니다.

- 병렬 에이전트 오케스트레이터 앱은 포화 상태입니다. worktree 격리, diff 리뷰, PR·머지 흐름, 상태 알림이 기본 사양이 됐고, 칸반 UI 자체는 차별점이 아닙니다.
- 이슈→PR→리뷰는 플랫폼의 기본 기능이 됐습니다. 플랫폼들은 쓰기 권한자만 트리거, 자기 PR 승인 금지, 에이전트의 머지 금지 같은 가드레일을 함께 제공합니다.
- 리뷰가 신뢰받는 조건은 작성 컨텍스트와 분리된 새 세션, diff와 실행 증거, 구조화된 판정, 그리고 CI와 저장소 규칙 같은 결정적 게이트입니다. "다른 벤더라서 더 낫다"는 직접 증거는 약하므로, 주장하려면 자체 데이터가 필요합니다.
- 이슈·PR·코멘트의 텍스트로 에이전트를 탈취하는 사고가 2026년에 반복됐습니다. 작성자 게이트, 자격증명 격리, 출력 검사가 공개 사용의 전제입니다.
- 가장 가까운 이용자는 AI 구독이나 API 키를 여러 개 가진 1인 개발자(또는 2~3인 팀)입니다. 이들의 병목은 코드 생성이 아니라 검토와 신뢰입니다.

## 6. 제안하는 포지션

> **증거 없이는 아무것도 머지되지 않는, 교차 벤더 검증 파이프라인.** 한 에이전트가 쓰고, 다른 벤더의 에이전트가 diff를 읽고 테스트 결과를 보고 판정하며, 구조화된 승인 없이는 머지되지 않습니다. 내 구독, 내 머신, 내 GitHub에서 동작합니다.

- 주 이용자: 코딩 에이전트 구독이나 키를 둘 이상 쓰면서 개인·소규모 저장소를 관리하는 개발자.
- 대상이 아닌 이용자: 검증 능력이 없는 비개발자, 에이전트 수십 개를 동시에 돌리려는 팀, 조직 단위 거버넌스 플랫폼을 찾는 기업.
- 가장 잘해야 할 한 가지: 잘 정의된 이슈 하나를, 다른 벤더가 검증한 머지 가능한 PR로 바꾸고 사람은 마지막 승인만 하게 하는 것.
- 핵심 지표(제안): 이 저장소에 머지된 PR 가운데 MAO 파이프라인이 만든 것의 비율.

## 8. 유지보수자가 먼저 정해야 할 것

1. 이 프로젝트는 개인 도구입니까, 공개 제품입니까? 안전 기본값, 배포, 문서에 들일 노력이 여기서 갈립니다.
2. 장기적으로 남길 엔진은 무엇입니까? (N1)
3. 머지 전 사람 승인을 기본값으로 두는 데 동의합니까? (B3)
4. 공개 저장소에서 auto-trigger를 지원합니까? 지원한다면 신뢰 기준은 작성자 권한입니까, 승인 라벨입니까? (A1)
5. 저장 모델은 SQLite로 옮깁니까, "데이터 디렉터리 하나에 프로세스 하나"로 단순화합니까? (N4)
6. Windows에서 에이전트 실행을 지원합니까, 미지원으로 명시합니까?
7. 언어 정책은 무엇입니까? 지금은 README와 UI가 영어, 이슈가 한국어입니다. (E3)
8. 이름을 유지합니까? "MAO"는 같은 이름의 프로젝트가 여럿 있습니다([user-needs.md](user-needs.md)).
9. v0.1.1을 지금 정리해 출시하고 날짜 기반 릴리스로 바꿉니까? (N10)
10. 같은 작업을 여러 AI 도구로 구현해 비교하는 방식을 유지합니까? 비교에는 도움이 되지만, 3절과 4.5절의 중복 구현 비용이 따릅니다. 한 쪽짜리 설계 기록으로 대안을 비교하는 방법도 있습니다.

## 9. 한계

- 코드를 읽어서 내린 판단입니다. 테스트, 앱, 파이프라인은 실행하지 않았습니다.
- 감사와 리서치는 하위 에이전트가 수행했습니다. 2절의 사실은 코디네이터가 다시 확인했지만, 4절의 나머지 항목은 감사의 확인 수준(verified / likely)에 의존합니다. "likely"로 표시한 것은 이슈 작성 단계에서 다시 검증했습니다.
- 외부 리서치의 상당 부분은 2차 자료에 근거합니다. 문서마다 확인 수준을 표기했습니다.
- 열린 PR(#103, #107, #109, #110 등)이 머지되면 일부 항목의 전제가 달라집니다. 이슈에 착수하기 전에 현재 코드에서 전제를 다시 확인하십시오.
