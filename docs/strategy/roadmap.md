# MAO 장기 개발 계획 (제안)

- 작성일: 2026-11-12. 계획 기간: 2026-11 ~ 2028-05(18개월).
- 상태: **제안.** 근거는 [project-review-2026-11.md](project-review-2026-11.md)에 있습니다.
- 항목 id(`A1`, `N4` 등)는 이 문서와 이슈에서 공통으로 씁니다.

## 1. 목표와 원칙

**목표.** 잘 정의된 이슈 하나를, 다른 벤더의 에이전트가 검증한 머지 가능한 PR로 바꾸고, 사람은 마지막 승인만 하게 합니다.

**원칙.**

1. **증거 없이는 머지하지 않습니다.** 리뷰어는 diff와 실행 결과를 보고, 판정은 구조화하며, 머지 여부는 코드가 결정합니다.
2. **기본값은 사람 쪽에 둡니다.** 무인 진행과 자동 머지는 저장소별로 켜는 선택 사항이고, 신뢰가 쌓인 만큼만 넓힙니다.
3. **강제할 것은 코드로 강제합니다.** 에이전트에게 주는 산문 지시나 문서의 경고로 대신하지 않습니다.
4. **엔진도 구현도 하나만 둡니다.** 같은 기능을 두 엔진에, 같은 이슈를 여러 PR에 만들지 않습니다.
5. **릴리스는 날짜로, 범위는 사용자가 체감하는 변화로 정합니다.**

### 2.1 NOW — 믿을 수 있는 핵심 루프

**완료 조건.**

- diff를 본 리뷰어의 승인 판정 없이는 어떤 PR도 머지되지 않고, 이것을 hermetic e2e 테스트가 증명합니다.
- 신뢰할 수 없는 작성자의 이슈는 에이전트를 실행시키지 못합니다.

### 2.2 NEXT — 하나의 파이프라인, 보이는 실행

**완료 조건.**

- 엔진이 하나이고, GUI·CLI·Swarm이 같은 파이프라인을 씁니다. 리뷰가 수정을 요청하면 정해진 횟수 안에서 작성자에게 되돌아갑니다.

- maker-checker가 GitHub에서도 서로 다른 정체성의 실제 리뷰로 보입니다.
- 저장 모델에 대한 결정이 기록되고 이행됐습니다.
- `npx`나 `npm i -g`로 CLI를 설치할 수 있고, 릴리스가 날짜에 맞춰 나옵니다.
- 역할과 모델 조합의 해결률, 결함 탐지율, 비용을 수치로 말할 수 있습니다.

## 3. 지표와 전환 기준

**핵심 지표.** 이 저장소에 머지된 PR 가운데 MAO 파이프라인이 만든 것의 비율. 지금은 8월 초의 3건 이후 0입니다. 제안하는 목표는 2027-02에 30%, 2027-05에 50%입니다.

**주간 지표.** 마지막 릴리스 뒤 경과 일수(목표 14일 이하), PR 리드타임 중앙값, PR 크기 중앙값, 열린 PR 수, PR당 리뷰 라운드 수.

**평가 하네스 지표(N8 이후).** 시드 이슈 해결률, 심어 둔 결함의 리뷰 탐지율, 작업당 시간과 비용. 같은 계열 리뷰와 교차 계열 리뷰를 비교해 maker-checker 주장을 수치로 뒷받침하거나 고칩니다.

**전환 기준(2027-02 점검).** 다음 중 둘 이상이면 Electron GUI와 4단계 파이프라인을 접고 L1(교차 벤더 리뷰 게이트)로 좁히는 것을 검토합니다.

- 핵심 지표가 30% 미만입니다.
- 평가 픽스처에서 파이프라인의 해결률이 단일 에이전트 세션보다 뚜렷이 낮습니다.
- 외부 사용자의 신호(스타, 외부 이슈, 외부 PR)가 없습니다.

## 4. 하지 않을 것

- 에이전트 수와 병렬 실행 규모 경쟁. 자금력 있는 제품들이 앞서 있고, 이용자 다수는 에이전트 하나를 씁니다.
- 범용 칸반 UI, 모바일·원격 감독 앱.
- 검증 능력이 없는 이용자를 위한 원클릭 자동 배포.
- 조직 단위 거버넌스 플랫폼, 호스팅 서비스.
- 구독 인증을 우회하는 기능.
- 범용 그래프 엔진, 서버형 내구 실행 엔진의 조기 도입. 필요한 것은 작은 상태 기계의 수정 루프와 단계별 멱등성입니다.
- 여러 에이전트가 동시에 쓰는 스웜. 쓰기는 한 줄기로, 병렬은 읽기와 검증에만 씁니다.
- MAO를 MCP 서버로 노출하는 일(당분간). 새로운 신뢰 경계가 생깁니다.

근거는 [benchmarking.md](benchmarking.md)와 [user-needs.md](user-needs.md)에 있습니다.

## 6. 운영 규칙 제안

**위험 등급.** 리뷰 지적과 하드닝 요청을 같은 무게로 다루지 않기 위한 기준입니다.

| 등급 | 대상 | 요구 |
| --- | --- | --- |
| 1 | GitHub에 쓰거나 머지하는 경로, 토큰을 다루는 경로, 에이전트 권한 플래그 | hermetic e2e 시나리오와 사람의 최종 확인 |
| 2 | 로컬 데이터 손실 | 단위 테스트 |
| 3 | UI와 UX | 렌더러 테스트 하나 |
| 4 | 문서, 테스트 인프라 | 릴리스를 막지 않음 |

**흐름.**

- 동시에 열린 PR은 draft를 포함해 2개까지(지금 7개).
- 테스트를 뺀 diff는 400줄 안팎까지. 넘으면 나눕니다.
- 리뷰는 두 라운드까지. 세 번째 라운드의 지적은 새 이슈로 보냅니다. 지적은 "이 PR이 만든 회귀"와 "원래 있던 결함"으로 나누고, 뒤쪽은 별도 이슈로 다룹니다.
- 이슈 하나에 구현 PR 하나. 대안 비교가 필요하면 한 쪽짜리 설계 기록으로 합니다.
- 하드닝 이슈를 열 때 "실제로 겪은 일인가, 리뷰에서 떠올린 가정인가"를 적습니다. 가정이면 하루로 제한합니다.
- 범위를 넓히거나 줄인 결정은 `docs/adr/`에 남깁니다.
